# Руководство для ИИ: особенности класса и подкласса → JSON

Версия контракта: 3.0  
Используется вместе с: `AI_CLASS_SUBCLASS_JSON_GUIDE.md`  
Целевой билдер: `class_package_builder.py → feat_builder.py`

## 1. Цель

Файл особенностей содержит единый JSON-массив всех особенностей, техник и
вариантов выбора класса и подкласса. Задача нейросети — не просто сохранить
описание правила, а явно задать каждую поддерживаемую механику:

- кнопку;
- тип действия;
- атаку или спасбросок;
- урон, лечение или произвольный бросок;
- дистанцию, цель и область;
- расход и восстановление;
- общий ресурс;
- Active Effect;
- честно перечисленную ручную часть.

При `schema_version: 2` и `strict_automation: true` в манифесте каждая
особенность обязана содержать объект `automation`.

## 2. Минимальный объект

```json
{
  "key": "feature:пепельный-рывок",
  "name": "Пепельный рывок",
  "requirements": "Хранитель Пепла 2",
  "description": "<p>Полный текст правил.</p>",
  "automation": {
    "mode": "partial",
    "manual": [
      "Игрок вручную перемещает токен в выбранную точку."
    ]
  },
  "mechanics": {
    "activity_type": "utility",
    "activity_name": "Пепельный рывок",
    "activation": {
      "type": "bonus",
      "value": 1
    }
  }
}
```

Обязательные поля:

- `key`;
- `name`;
- `description`;
- `automation`.

Рекомендуемые поля:

- `requirements`;
- `mechanics` для активной или автоматизированной пассивной механики;
- `uses` для собственных использований;
- `resource_pool` для владельца общего ресурса.

Допустимые необязательные поля верхнего уровня:

- `img`;
- `feature_type`;
- `properties`.

Не создавай вручную `_id`, UUID, `system`, `_stats`, `folder`, `sort`,
`ownership`, готовые activities или служебные поля Foundry.

## 3. Контракт автоматизации

```json
{
  "automation": {
    "mode": "partial",
    "manual": [
      "Ограничение одного раза за ход отслеживается вручную."
    ],
    "requires": [
      "midi-qol",
      "dae"
    ]
  }
}
```

Допустимые `mode`:

- `full` — всё правило выполняется созданными activity, расходами и эффектами;
- `partial` — полезная часть автоматизирована, остаток перечислен в `manual`;
- `manual` — правило применяется вручную;
- `passive` — особенность не требует кнопки; она либо информационная, либо
  содержит постоянный переносимый Active Effect.

Правила:

- `partial` требует непустой массив `manual`;
- `full` требует хотя бы одну activity или Active Effect;
- `passive` не создаёт нажимаемую activity;
- `manual` не должен притворяться полной автоматизацией;
- `requires` перечисляет только реально необходимые модули;
- наличие Midi-QOL или DAE не означает, что сложное правило автоматически
  поддерживается.

Если правило содержит несколько частей, оцени полноту всей особенности, а не
только одной кнопки.

## 4. Полный текст правила

`description` всегда содержит полное понятное правило, даже если оно полностью
автоматизировано. Укажи:

- тип действия или триггер;
- дистанцию и цель;
- расход;
- бросок атаки или спасбросок;
- формулу и тип урона/лечения;
- результат успеха и провала;
- длительность;
- восстановление;
- ограничения частоты;
- ручную часть.

Automation не заменяет текст правил.

## 5. Пассивные особенности

### 5.1. Информационный или системно неподдерживаемый пассив

```json
{
  "key": "feature:дополнительная-атака",
  "name": "Дополнительная атака",
  "requirements": "Хранитель Пепла 5",
  "description": "<p>Когда вы совершаете действие Атака, вы можете атаковать дважды вместо одного раза.</p>",
  "automation": {
    "mode": "manual",
    "manual": [
      "Число атак применяется игроком при совершении действия Атака."
    ]
  }
}
```

### 5.2. Постоянный подтверждённый Active Effect

```json
{
  "key": "feature:стойкость-к-холоду",
  "name": "Стойкость к холоду",
  "description": "<p>Вы получаете сопротивление урону холодом.</p>",
  "automation": {
    "mode": "passive"
  },
  "mechanics": {
    "passive": true,
    "effects": [
      {
        "name": "Сопротивление холоду",
        "transfer": true,
        "changes": [
          {
            "key": "system.traits.dr.value",
            "mode": "add",
            "value": "cold"
          }
        ]
      }
    ]
  }
}
```

Используй системный путь только если он подтверждён эталоном или официальным
руководством Active Effects для целевой версии D&D5e.

Не создавай предполагаемый Active Effect для:

- постоянного увеличения характеристики с нестандартным максимумом;
- изменения текущих или максимальных HP через `system.attributes.hp.value/max`;
- механики, зависящей от сложного условия;
- правила, для которого неизвестен точный системный путь.

Например, «Телосложение и Мудрость увеличиваются на 2, максимум до 22» нельзя
честно считать полностью автоматизированным простым `add` к
`system.abilities.*.value`. До отдельной поддержки билдера оставь такую часть
ручной или используй подтверждённый advancement, если он точно соответствует
правилу.

## 6. Одна activity

Поддерживаемые типы:

- `attack`;
- `save`;
- `damage`;
- `heal`;
- `utility`.

Общие поля:

```json
{
  "mechanics": {
    "activity_type": "utility",
    "activity_name": "Название кнопки",
    "activation": {
      "type": "reaction",
      "value": 1,
      "condition": "После получения урона"
    },
    "duration": {
      "value": 1,
      "units": "round"
    },
    "targeting": {
      "range": {
        "value": 30,
        "units": "ft"
      },
      "affects": {
        "type": "creature",
        "count": "1",
        "choice": true
      },
      "prompt": true
    }
  }
}
```

Допустимые `activation.type`:

- `action`;
- `bonus`;
- `reaction`;
- `special`;
- `none`.

`legendary` и `lair` технически поддерживаются общим feat-builder, но не
используются для обычных особенностей персонажа.

Для `special` и `none` ставь `value: null`. Условие активации записывай в
`condition`, а не только в описании.

Допустимые единицы длительности:

- `turn`;
- `round`;
- `minute`;
- `hour`;
- `day`.

## 7. Атака

```json
{
  "mechanics": {
    "activity_type": "attack",
    "activity_name": "Клинок пепла",
    "activation": {
      "type": "action",
      "value": 1
    },
    "attack": {
      "ability": "wis",
      "bonus": "",
      "flat": false,
      "type": "melee",
      "classification": "weapon"
    },
    "damage": [
      {
        "formula": "1d8 + @abilities.wis.mod",
        "type": "fire"
      }
    ],
    "targeting": {
      "range": {
        "value": 5,
        "units": "ft"
      },
      "affects": {
        "type": "creature",
        "count": "1"
      }
    }
  }
}
```

Фиксированная полная прибавка атаки:

```json
{
  "attack": {
    "ability": "none",
    "bonus": "+9",
    "flat": true,
    "type": "ranged",
    "classification": "spell"
  }
}
```

Не добавляй модификатор характеристики второй раз в `bonus`. `damage` должен
содержать всю формулу урона, включая модификатор, если он нужен правилу.

## 8. Спасбросок

Сл от классовой характеристики:

```json
{
  "save": {
    "ability": "con",
    "dc_formula": "@abilities.wis.dc"
  }
}
```

Фиксированная Сл:

```json
{
  "save": {
    "ability": "dex",
    "dc": 17
  }
}
```

Урон и результат успеха:

```json
{
  "damage": [
    {
      "formula": "2d8",
      "type": "thunder"
    }
  ],
  "on_save": "half"
}
```

Допустимые `on_save`:

- `none`;
- `half`;
- `full`.

Не записывай в `save.ability` характеристику класса. Там находится
характеристика спасброска цели. Характеристика класса задаётся формулой Сл.

## 9. Урон, лечение и произвольный бросок

### Урон без атаки

```json
{
  "mechanics": {
    "activity_type": "damage",
    "activity_name": "Дополнительный урон",
    "activation": {
      "type": "special",
      "value": null,
      "condition": "После попадания оружием"
    },
    "damage": [
      {
        "formula": "@scale.ash-warden.ash-die",
        "type": "force"
      }
    ]
  }
}
```

### Лечение или временные HP

```json
{
  "mechanics": {
    "activity_type": "heal",
    "activity_name": "Защитный контур",
    "activation": {
      "type": "bonus",
      "value": 1
    },
    "healing": {
      "formula": "@scale.ash-warden.ash-die + @abilities.wis.mod",
      "type": "temphp"
    }
  }
}
```

`healing.type`:

- `healing`;
- `temphp`.

### Произвольный отображаемый бросок

```json
{
  "mechanics": {
    "activity_type": "utility",
    "activity_name": "Бросить кость пепла",
    "roll": {
      "formula": "@scale.ash-warden.ash-die",
      "name": "Кость пепла",
      "prompt": false,
      "visible": true
    }
  }
}
```

Utility-roll показывает результат, но не наносит урон и не лечит.

## 10. Формулы и ScaleValue

Кость класса:

```text
@scale.ash-warden.ash-die
```

Кость подкласса:

```text
@scale.glass-flame.shard-die
```

Части кости:

```text
@scale.glass-flame.shard-die.number
@scale.glass-flame.shard-die.faces
```

Четыре независимые кости текущего размера:

```text
4d@scale.glass-flame.shard-die.faces
```

Нельзя использовать:

```text
4 * @scale.glass-flame.shard-die
```

Последняя формула бросает одну кость и умножает один результат на четыре.

После `@scale.` всегда идёт `identifier` владельца шкалы. Для шкалы подкласса
это идентификатор подкласса.

## 11. Собственные использования особенности

```json
{
  "uses": {
    "max": "1",
    "spent": 0,
    "recovery": [
      {
        "period": "lr",
        "type": "recoverAll"
      }
    ]
  }
}
```

Формула максимума допустима:

```json
{
  "max": "@prof"
}
```

Допустимые периоды:

- `recharge`;
- `sr`;
- `lr`;
- `day`;
- `dawn`;
- `dusk`.

У одной activity собственное использование расходуется автоматически. При
нескольких activities по умолчанию его расходует первая; для другой activity
явно укажи `consume_uses`.

## 12. Общий ресурс класса

### 12.1. Особенность-владелец

```json
{
  "key": "feature:ядро-пепла",
  "name": "Ядро пепла",
  "requirements": "Хранитель Пепла 1",
  "description": "<p>Вы обладаете общим запасом очков пепла.</p>",
  "automation": {
    "mode": "passive"
  },
  "resource_pool": {
    "key": "ash",
    "label": "Очки пепла",
    "max": "@scale.ash-warden.ash-points",
    "recovery": [
      {
        "period": "sr",
        "type": "recoverAll"
      },
      {
        "period": "lr",
        "type": "recoverAll"
      }
    ]
  }
}
```

Один `resource_pool.key` объявляется ровно одной особенностью.

### 12.2. Расход

```json
{
  "resource": {
    "type": "pool",
    "target": "ash",
    "value": "2",
    "operation": "consume"
  }
}
```

`target` посимвольно совпадает с `resource_pool.key`. Применение блокируется,
если ресурса недостаточно.

### 12.3. Восстановление кнопкой

```json
{
  "mechanics": {
    "activity_type": "utility",
    "activity_name": "Восстановить пепел",
    "activation": {
      "type": "special",
      "value": null,
      "condition": "Только если запас очков пепла пуст"
    },
    "resource": {
      "type": "pool",
      "target": "ash",
      "value": "2",
      "operation": "restore",
      "require_empty": true
    }
  }
}
```

`operation`:

- `consume` — потратить;
- `restore` — восстановить.

`require_empty: true` разрешает восстановление только при нулевом остатке.
Восстановление не превышает максимум пула.

Не расходуй `ScaleValue` напрямую. ScaleValue задаёт максимум или формулу, а
текущий остаток хранится в `resource_pool`.

## 13. Несколько activities

```json
{
  "mechanics": {
    "activities": [
      {
        "type": "utility",
        "activity_name": "Наложить печать",
        "activation": {
          "type": "bonus",
          "value": 1
        },
        "resource": {
          "type": "pool",
          "target": "ash",
          "value": "1",
          "operation": "consume"
        }
      },
      {
        "type": "damage",
        "activity_name": "Урон печати",
        "activation": {
          "type": "special",
          "value": null,
          "condition": "После попадания по отмеченной цели; не чаще одного раза в ход"
        },
        "damage": [
          {
            "formula": "@scale.glass-flame.shard-die",
            "type": "force"
          }
        ]
      }
    ]
  }
}
```

Общие поля `mechanics` наследуются activities, а поля конкретной activity их
заменяют. Указывай расход отдельно у каждой кнопки, которая должна его
производить.

## 14. Цели и области

Обычная область:

```json
{
  "targeting": {
    "range": {
      "value": 60,
      "units": "ft"
    },
    "template": {
      "type": "radius",
      "size": 20,
      "units": "ft"
    },
    "affects": {
      "type": "creature",
      "count": "",
      "choice": false
    }
  }
}
```

Если правило поражает всех подходящих существ в области, используй
`choice: false`. Билдер включает автоматический поиск и подтверждение целей.

Если правило говорит «существа по вашему выбору», используй `choice: true`.
Автоматический выбор всех токенов будет отключён, чтобы не затронуть
нежелательные цели.

Не заполняй `affects.special`, если обычных полей достаточно.

## 15. Active Effects

### Состояние при провале спасброска

```json
{
  "effects": [
    {
      "name": "Сбит с ног",
      "status": "prone",
      "on_save": false,
      "duration": {
        "value": 1,
        "units": "round"
      },
      "special_duration": [
        "turnStartSource"
      ]
    }
  ]
}
```

### Подтверждённое изменение параметра

```json
{
  "effects": [
    {
      "name": "Бонус к КД",
      "changes": [
        {
          "key": "system.attributes.ac.bonus",
          "mode": "add",
          "value": "2"
        }
      ]
    }
  ]
}
```

Допустимые режимы:

- `custom`;
- `multiply`;
- `add`;
- `downgrade`;
- `upgrade`;
- `override`.

При нескольких activities привяжи эффект по индексу или точному имени:

```json
{
  "activity": 1
}
```

Постоянный эффект использует `transfer: true` и не обязан быть привязан к
activity. Применяемый эффект без `transfer` должен быть связан с activity.

Не создавай непроверенные системные пути. Лучше честный `partial`, чем
неработающий Active Effect.

## 16. Что остаётся ручным без специального runtime

Обычно нельзя объявлять полностью автоматическими:

- перемещение и телепортацию токена;
- выбор точки появления;
- автоматическую реакцию на произвольное внешнее событие;
- изменение уже полученного урона;
- ограничение «один раз за ход»;
- сложную связь метки с конкретной целью;
- запрет телепортации;
- изменение чужого броска после его совершения;
- несколько независимых концентраций;
- возврат ресурса по условию произвольного броска;
- постоянное повышение характеристики с изменённым максимумом;
- выбор сопротивления после отдыха;
- смену настроенного оружия.

Автоматизируй поддерживаемую часть: кнопку, бросок, расход, область или эффект.
Остаток перечисли в `automation.manual`.

## 17. Запрещённые подмены

Нельзя:

- объявлять `full`, если работает только кнопка с описанием;
- создавать `utility`, когда правило должно наносить урон или лечить;
- использовать описание вместо `damage`, `healing` или `save`;
- добавлять фиктивный Active Effect к неизвестному пути;
- дублировать один расход как `uses` и `resource`;
- создавать отдельный запас в каждой технике общего ресурса;
- использовать шкалу как текущий остаток;
- умножать одну кость, когда правило требует несколько независимых костей;
- давать не-кастеру spellcasting-прогрессию ради Сл способностей;
- скрывать ручные ограничения из `automation.manual`.

## 18. Самопроверка массива особенностей

1. Корень файла — JSON-массив.
2. Каждый `key` уникален и начинается с `feature:`.
3. У каждого объекта есть `name`, `description` и `automation`.
4. Все активные правила имеют `mechanics`.
5. `full` действительно создаёт activity или эффект и не имеет скрытой ручной
   части.
6. `partial` содержит непустой `manual`.
7. `passive` не создаёт activity.
8. У каждого собственного расхода есть `uses`.
9. Каждый общий расход ссылается на существующий `resource_pool`.
10. Каждый пул объявлен ровно один раз.
11. У спасброска есть характеристика и Сл.
12. У урона и лечения есть формула и тип.
13. Формула шкалы использует идентификатор владельца.
14. Несколько костей записаны как несколько костей.
15. Выборочная область имеет `choice: true`.
16. Применяемый Active Effect привязан к activity.
17. Постоянный Active Effect имеет `transfer: true`.
18. Неподдерживаемая часть сохранена и в описании, и в `automation.manual`.
19. В JSON нет `_id`, UUID и готовых системных activities Foundry.


## 19. Уточнения после переноса воина Warcraft

- `prerequisites` допускает системные `items` (например, `class:warcraft-warrior`),
  `level` и `repeatable`. Требование уровня сохраняется для проверки ItemChoice.
  Для классового выбора уровень проверяется в контексте advancement; отдельно
  проверьте этот случай при мультиклассе в живой Foundry.
- Иконка `img` особенности наследуется её activities и эффектами, если у них
  нет собственной. Пустое имя activity заменяется названием особенности.
- `resource_pool.initial_empty: true` обнуляет остаток при добавлении владельца
  пула на Actor (через spent = max). Экспорт в компендиуме не расходуется.
- `resource.operation` поддерживает consume, restore и clear. Clear обнуляет
  остаток; для него используйте value: "0".
- Чтобы кнопка резерва одновременно восстанавливала общий пул и тратила своё
  ограниченное использование, задайте собственные `uses`, ресурс с restore и
  `mechanics.consume_uses: true`.
- Runtime добавляет изменение пула в штатный `dnd5e.activityConsumption`, вместе
  с нативными расходами. Отмена окна применения не вызывает отдельного расхода
  после создания сообщения. Повторное postUse-списание удалено.
- Частота, условия события и истечение часа не отслеживаются этим runtime.
  Не обозначайте их полной автоматизацией.
- Проверка runtime: `node tests/test_resource_runtime.mjs` (моки API); игровой
  тест в Foundry всё равно требуется.
