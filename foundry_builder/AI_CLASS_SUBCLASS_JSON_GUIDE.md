> предыстории, черты и заклинания описаны в `AI_CONTENT_PACKAGE_GUIDE.md`.

# Руководство для ИИ: авторский класс и подкласс → пакет JSON

Версия контракта: 3.0  
Целевая цепочка: `class_package_builder.py → class_builder.py + subclass_builder.py + feat_builder.py → foundry_module_builder.py`  
Целевая среда: Foundry VTT 13.351, D&D5e 5.3.3

## 1. Готовая инструкция для нейросети

Придумай и создай один полноценный авторский класс D&D 5e и один подкласс к
нему. Подготовь компактный пакет JSON для билдеров проекта.

Результат должен содержать четыре отдельных файла:

1. `<class_identifier>_class.json` — класс;
2. `<subclass_identifier>_subclass.json` — подкласс;
3. `<class_identifier>_features.json` — единый массив всех особенностей,
   техник и вариантов выбора класса и подкласса;
4. `<class_identifier>_package_manifest.json` — манифест пакета.

Обязательные требования:

- разработай цельную игровую механику и прогрессию с 1-го по 20-й уровень;
- создай все особенности, на которые ссылаются класс и подкласс;
- не оставляй активную механику только в описании;
- для каждой особенности используй контракт автоматизации из
  `AI_FEATURE_JSON_GUIDE.md`;
- не выдумывай `_id`, UUID, системные пути Active Effect или ключи Trait;
- используй символические ссылки `feature:...`; упаковщик сам создаст ID и UUID;
- не добавляй классу ячейки заклинаний, если он фактически не владеет магией;
- верни только четыре требуемых файла, без готовых экспортов Foundry и без
  дополнительных служебных JSON.

Если пользователь не задал тему, роль или механику, нейросеть придумывает их
самостоятельно. Уточняющий вопрос нужен только при прямом противоречии в
требованиях пользователя.

## 2. Что именно создаёт нейросеть

Нейросеть создаёт компактные авторские данные. Билдеры создают:

- стабильные `_id`;
- реальные compendium UUID;
- системные объекты `advancement`;
- Foundry Item класса, подкласса и особенностей;
- LevelDB-компендиумы и устанавливаемый модуль.

Не копируй полный экспорт Foundry. Не создавай вручную `system`, `_stats`,
`ownership`, `folder`, `sort`, `_key` и служебные `flags`, кроме явно
разрешённых полей руководства особенностей.

## 3. Общие идентификаторы

`identifier`:

- содержит только `a-z`, `0-9` и `-`;
- начинается с буквы или цифры;
- уникален внутри пакета;
- после первого выпуска не меняется.

Пример:

```json
{
  "class_identifier": "ash-warden",
  "subclass_identifier": "glass-flame"
}
```

Ключ особенности имеет вид `feature:<slug>`. Часть после `feature:` должна
быть уникальной и стабильной:

```json
{
  "key": "feature:пепельный-рывок"
}
```

Русский текст после `feature:` разрешён. Регистр, пробелы и написание ссылки
нельзя менять между файлами.

## 4. Манифест пакета

Обязательный файл `<class_identifier>_package_manifest.json`:

```json
{
  "schema_version": 2,
  "strict_automation": true,
  "identifier": "ash-warden",
  "name": "Хранитель Пепла: Стеклянное Пламя",
  "class_file": "ash-warden_class.json",
  "subclass_file": "glass-flame_subclass.json",
  "features_file": "ash-warden_features.json"
}
```

Правила:

- `schema_version` всегда `2`;
- `strict_automation` всегда `true`;
- `identifier` совпадает с `identifier` класса;
- пути указывают на три файла в той же папке;
- манифест не содержит сами объекты класса, подкласса или особенностей.

## 5. JSON класса

Минимальный рабочий каркас:

```json
{
  "schema_version": 1,
  "type": "class",
  "name": "Хранитель Пепла",
  "identifier": "ash-warden",
  "description": "<p>Краткое описание роли и источника силы класса.</p>",
  "levels": 1,
  "hit_die": "d10",
  "primary_abilities": ["con", "wis"],
  "primary_all": false,
  "spellcasting": {
    "progression": "none",
    "ability": ""
  },
  "properties": [],
  "starting_equipment": [],
  "wealth": "",
  "advancement": [
    {"type": "hit_points"},
    {"type": "subclass", "level": 3}
  ]
}
```

### Поля класса

| Поле | Обязательно | Правило |
|---|---:|---|
| `schema_version` | да | Всегда `1`. |
| `type` | да | Всегда `"class"`. |
| `name` | да | Отображаемое русское название. |
| `identifier` | да | Стабильный системный идентификатор. |
| `description` | да | Обзор класса; не дублирует полный текст отдельных особенностей. |
| `levels` | да | Для нового класса всегда `1`. |
| `hit_die` | да | `d4`, `d6`, `d8`, `d10` или `d12`. |
| `primary_abilities` | да | Массив из `str`, `dex`, `con`, `int`, `wis`, `cha`. |
| `primary_all` | нет | Обычно `false`; `true` означает, что все характеристики считаются основными. |
| `spellcasting` | да | Магическая прогрессия класса. |
| `properties` | нет | Только подтверждённые системные ключи. Обычно `[]`. |
| `starting_equipment` | нет | Только если формат точно взят из эталона. Иначе `[]`. |
| `wealth` | нет | Формула стартового золота или пустая строка. |
| `advancement` | да | Полная прогрессия класса. |

Допустимые `spellcasting.progression`:

- `none`;
- `full`;
- `half`;
- `third`;
- `pact`;
- `artificer`.

Если класс не использует заклинания:

```json
{
  "spellcasting": {
    "progression": "none",
    "ability": ""
  }
}
```

Нельзя ставить `half`, `third` или другую прогрессию только потому, что класс
использует магический ресурс, мистические техники, Сл от характеристики или
сверхъестественные эффекты. Прогрессия, отличная от `none`, создаёт ячейки
заклинаний.

## 6. JSON подкласса

Минимальный рабочий каркас:

```json
{
  "schema_version": 1,
  "type": "subclass",
  "name": "Стеклянное Пламя",
  "identifier": "glass-flame",
  "class_identifier": "ash-warden",
  "description": "<p>Краткое описание специализации.</p>",
  "spellcasting": {
    "progression": "none",
    "ability": ""
  },
  "advancement": []
}
```

### Поля подкласса

| Поле | Обязательно | Правило |
|---|---:|---|
| `schema_version` | да | Всегда `1`. |
| `type` | да | Всегда `"subclass"`. |
| `name` | да | Отображаемое русское название. |
| `identifier` | да | Стабильный идентификатор подкласса. |
| `class_identifier` | да | Посимвольно совпадает с `identifier` класса. |
| `description` | да | Обзор подкласса. |
| `spellcasting` | да | Только магия, которую добавляет сам подкласс. |
| `advancement` | да | Выдача особенностей, выборы, Trait и ScaleValue подкласса. |

Подкласс не содержит:

- `hit_die`;
- `primary_abilities`;
- `hit_points`;
- `subclass`;
- `asi`;
- стартовое снаряжение;
- обычную классовую прогрессию характеристик.

Если базовый класс уже является заклинателем, а подкласс не меняет его
прогрессию, у подкласса всё равно ставится `progression: "none"`.

## 7. Допустимые записи `advancement`

Поддерживаются только:

- `hit_points`;
- `subclass`;
- `asi`;
- `trait`;
- `item_grant`;
- `item_choice`;
- `scale`.

Не придумывай другие типы.

### 7.1. Хиты

Только у класса и ровно один раз:

```json
{"type": "hit_points"}
```

### 7.2. Выбор подкласса

Только у класса и не более одного раза:

```json
{"type": "subclass", "level": 3}
```

Уровень определяется дизайном класса и может быть 1–20. Первая особенность
созданного подкласса должна выдаваться на этом же уровне.

### 7.3. Обычное повышение характеристик

Только у класса:

```json
{
  "type": "asi",
  "level": 4,
  "points": 2,
  "cap": 2
}
```

Для каждого уровня используется отдельная запись. Не добавляй ASI подклассу.

Фиксированное повышение допустимо только когда оно подтверждено механикой и
проверено билдером:

```json
{
  "type": "asi",
  "level": 20,
  "points": 0,
  "fixed": {
    "con": 2,
    "wis": 2
  },
  "locked": ["con", "wis"],
  "cap": 2
}
```

`cap` не следует трактовать как новый максимум значения характеристики.
Механику вида «+2, максимум до 22» нельзя объявлять полностью
автоматизированной без отдельной подтверждённой поддержки билдера. Не
подменяй её Active Effect с непроверенным сложением.

### 7.4. Владения и Trait

```json
{
  "type": "trait",
  "level": 1,
  "title": "Владения основного класса",
  "class_restriction": "primary",
  "grants": [
    "armor:lgt",
    "armor:med",
    "weapon:sim",
    "saves:con",
    "saves:wis"
  ],
  "choices": [
    {
      "count": 2,
      "pool": ["skills:*"]
    }
  ]
}
```

`class_restriction`:

- `primary` — только если класс взят первым;
- `secondary` — только при мультиклассировании;
- отсутствует — без ограничения.

Внутренние ключи `grants` и `choices.pool` бери только из эталонных каталогов.
Если нужного ключа нет в каталогах, не угадывай его: перенеси правило в
особенность и укажи ручную часть.

### 7.5. Автоматическая выдача особенностей

```json
{
  "type": "item_grant",
  "level": 2,
  "title": "Особенности 2-го уровня",
  "items": [
    {
      "ref": "feature:пепельный-рывок",
      "optional": false
    }
  ]
}
```

На одном уровне можно выдать несколько особенностей одним `item_grant`.
`optional: false` означает обязательную выдачу. Для необязательных вариантов
обычно нужен `item_choice`, а не optional grant.

Не пиши `uuid`. В новом авторском пакете используй только `ref`.

### 7.6. Выбор особенности

```json
{
  "type": "item_choice",
  "title": "Пепельная техника",
  "item_type": "feat",
  "allow_drops": false,
  "choices": {
    "2": {
      "count": 2,
      "replacement": false
    },
    "6": {
      "count": 1,
      "replacement": false
    },
    "10": {
      "count": 1,
      "replacement": true
    }
  },
  "pool": [
    "feature:техника-пепельный-щит",
    "feature:техника-угольный-шаг",
    "feature:техника-вспышка"
  ]
}
```

Правила:

- уровень находится в ключе объекта `choices`;
- `replacement: false` добавляет новый выбор;
- `replacement: true` заменяет один ранее выбранный вариант;
- все элементы `pool` существуют в файле особенностей;
- выбранные варианты не выдаются дополнительно через `item_grant`;
- при полном известном пуле ставь `allow_drops: false`.

### 7.7. Масштабируемое число

```json
{
  "type": "scale",
  "title": "Очки пепла",
  "identifier": "ash-points",
  "scale_type": "number",
  "scale": {
    "1": {"value": 2},
    "5": {"value": 3},
    "11": {"value": 4},
    "17": {"value": 5}
  }
}
```

### 7.8. Масштабируемая кость

```json
{
  "type": "scale",
  "title": "Кость пепла",
  "identifier": "ash-die",
  "scale_type": "dice",
  "scale": {
    "1": {
      "number": 1,
      "faces": 6,
      "modifiers": []
    },
    "9": {
      "number": 1,
      "faces": 8,
      "modifiers": []
    },
    "17": {
      "number": 1,
      "faces": 10,
      "modifiers": []
    }
  }
}
```

Также поддерживаются `string` и `distance`, но используй их только по
эталонному формату.

Идентификатор каждой шкалы уникален внутри своего класса или подкласса.
Шкала — значение для формул, а не текущий расходуемый запас. Для расходуемого
запаса обязательно создай `resource_pool` в особенности.

Шкалы D&D5e могут не отображаться на листе персонажа как отдельный ресурс. Если
игроку нужна видимая кнопка броска шкалы, создай отдельную utility-особенность,
которая бросает эту формулу.

## 8. Формулы класса и подкласса

Шкала класса:

```text
@scale.ash-warden.ash-die
```

Шкала подкласса:

```text
@scale.glass-flame.shard-die
```

После `@scale.` всегда используется `identifier` владельца шкалы:

- для шкалы класса — `class.identifier`;
- для шкалы подкласса — `subclass.identifier`, не `class_identifier`.

Полные правила формул приведены в `AI_FEATURE_JSON_GUIDE.md`.

## 9. JSON особенностей

Файл `<class_identifier>_features.json` содержит один JSON-массив:

```json
[
  {
    "key": "feature:ядро-пепла",
    "name": "Ядро пепла",
    "requirements": "Хранитель Пепла 1",
    "description": "<p>Полный текст особенности.</p>",
    "automation": {
      "mode": "passive"
    },
    "resource_pool": {
      "key": "ash",
      "label": "Очки пепла",
      "max": "@scale.ash-warden.ash-points",
      "recovery": [
        {
          "period": "lr",
          "type": "recoverAll"
        }
      ]
    }
  }
]
```

Каждый объект создаётся строго по `AI_FEATURE_JSON_GUIDE.md`.

## 10. Обязательная связность четырёх файлов

Перед выдачей проверь:

1. `manifest.identifier == class.identifier`.
2. `subclass.class_identifier == class.identifier` посимвольно.
3. Каждый `ref` из `item_grant` существует как `features[].key`.
4. Каждый элемент `item_choice.pool` существует как `features[].key`.
5. Каждый `features[].key` уникален.
6. Нет неиспользуемых особенностей: каждая выдается или входит в пул выбора.
7. Особенность-владелец общего ресурса выдаётся не позже первой техники,
   которая этот ресурс расходует.
8. Каждый `resource.target` совпадает с одним `resource_pool.key`.
9. Каждый `ScaleValue` используется с идентификатором своего владельца.
10. Уровни особенностей в `requirements` совпадают с уровнями выдачи.
11. Первая особенность подкласса выдаётся на уровне выбора подкласса.
12. Ни класс, ни подкласс не ссылаются на несуществующие UUID.

## 11. Требования к дизайну класса

Для тестового или полноценного класса соблюдай следующие правила:

- у класса есть ясная роль, основной игровой цикл и ограничение ресурса;
- механика не является простым переименованием официального класса;
- базовые способности работают без подкласса;
- подкласс развивает механику класса, а не заменяет её другой системой;
- ключевые уровни не остаются пустыми без причины;
- активные способности имеют цену, ограничение использования или понятную
  альтернативную стоимость;
- постоянные бонусы и ресурсы не дублируются в нескольких особенностях;
- одна и та же способность не выдаётся одновременно через `item_grant` и
  `item_choice`;
- текст правил использует однозначные значения: действие, дистанцию, цель,
  длительность, формулу, спасбросок, успех, провал и восстановление;
- если механика не поддерживается билдером, она честно помечается как
  `partial` или `manual`, а не имитируется неверным эффектом.

## 12. Правильное размещение механики

| Механика | Где задавать |
|---|---|
| Кость хитов | `class.hit_die` |
| Основные характеристики | `class.primary_abilities` |
| Ячейки заклинаний | `class.spellcasting` или собственная прогрессия подкласса |
| Выбор подкласса | `class.advancement: subclass` |
| Обычный ASI | `class.advancement: asi` |
| Владения | `advancement: trait` |
| Выдача особенности | `advancement: item_grant` |
| Выбор техники | `advancement: item_choice` |
| Масштабируемая формула | `advancement: scale` |
| Текущий общий запас | `features[].resource_pool` |
| Кнопка, атака, спасбросок, урон, лечение | `features[].mechanics` |
| Постоянный подтверждённый эффект | `features[].mechanics.effects` |
| Неподдерживаемое правило | `description` + `automation.manual` |

Не дублируй одну механику в нескольких слоях.

## 13. Алгоритм работы нейросети

1. Определи тему, роль, основные характеристики и игровой цикл класса.
2. Реши, является ли класс заклинателем. Если нет — зафиксируй `none`.
3. Составь таблицу прогрессии 1–20 вне итогового JSON.
4. Определи уровень выбора подкласса и уровни его особенностей.
5. Перечисли все обязательные и выбираемые особенности.
6. Спроектируй шкалы и общие ресурсы.
7. Создай полный массив особенностей по руководству особенностей.
8. Создай класс и подкласс с символическими ссылками.
9. Создай манифест схемы 2.
10. Проведи перекрёстную проверку всех ссылок, уровней, ресурсов и формул.
11. Если доступны скрипты проекта, запусти упаковщик и тесты.
12. Исправь все ошибки до передачи файлов.

## 14. Формат ответа нейросети

Предпочтительный результат — четыре прикреплённых файла.

Если интерфейс не умеет создавать файлы, выведи четыре блока в таком порядке:

1. имя файла отдельной строкой;
2. один fenced-блок `json`;
3. никаких комментариев внутри JSON.

Не объединяй четыре документа в один произвольный объект. Не добавляй
пояснения между файлами, кроме их имён.

## 15. Финальная самопроверка

- [ ] Созданы ровно четыре требуемых файла.
- [ ] Все четыре файла являются корректным JSON.
- [ ] Манифест использует схему 2 и строгую автоматизацию.
- [ ] Класс имеет один `hit_points` и не более одного `subclass`.
- [ ] Подкласс не содержит запрещённых advancement.
- [ ] Все уровни находятся в диапазоне 1–20.
- [ ] Все идентификаторы стабильны и соответствуют формату.
- [ ] `class_identifier` совпадает с классом посимвольно.
- [ ] У не-кастера стоит `progression: "none"` и пустая `ability`.
- [ ] Все символические ссылки разрешаются в массиве особенностей.
- [ ] Все выбираемые особенности находятся в `item_choice.pool`.
- [ ] Все активные особенности содержат рабочую механику.
- [ ] Каждый общий ресурс объявлен ровно один раз.
- [ ] Восстановление и расход ресурсов явно заданы.
- [ ] Шкалы подкласса используют идентификатор подкласса.
- [ ] Несколько костей записаны как несколько костей, а не умножение одной.
- [ ] Неподдерживаемая автоматика честно перечислена как ручная.
- [ ] Не созданы фиктивные UUID, `_id` или системные поля Foundry.

## 16. Использование эталонных каталогов

`class_reference_catalog.json` и `subclass_reference_catalog.json` содержат
полные официальные или проверенные экспорты. Используй их:

- для проверки внутреннего формата Trait;
- для сравнения прогрессий заклинаний;
- для проверки структуры ScaleValue, ItemGrant и ItemChoice;
- для изучения реальных сочетаний advancement.

Каталоги — справочник, а не шаблон для слепого копирования. Компактный JSON
должен следовать этому руководству, даже если полный экспорт содержит больше
служебных полей.

## 17. Какие файлы дать нейросети

Минимальный обязательный комплект для создания JSON:

1. `AI_CLASS_SUBCLASS_JSON_GUIDE.md`;
2. `AI_FEATURE_JSON_GUIDE.md`;
3. `class_reference_catalog.json`;
4. `subclass_reference_catalog.json`.

Этого комплекта достаточно, чтобы придумать класс и подкласс и подготовить
четыре входных JSON.

Если нейросеть также должна сама запускать сборку и исправлять ошибки, передай
ей дополнительно:

1. `class_builder.py`;
2. `subclass_builder.py`;
3. `class_package_builder.py`;
4. актуальный `feat_builder.py`;
5. `midi_compat.py`;
6. `project_audit.py`;
7. `PROJECT_MANIFEST.json`.

`foundry_module_builder.py` нужен только если в той же задаче требуется собрать
устанавливаемый модуль Foundry. Для одной генерации входных JSON он не нужен.

Не нужно отправлять нейросети:

- все отдельные старые экспорты, уже объединённые в каталоги;
- готовые модули ранее собранных классов;
- LevelDB-паки;
- полный JSON ранее собранного класса как обязательный шаблон;
- NPC-, weapon-, spell- и equipment-билдеры.
