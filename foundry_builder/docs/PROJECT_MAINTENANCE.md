# Сопровождение проекта и канонического ZIP

Проект хранится в двух пользовательских файлах:

- `FoundryVTT_Builder_Project.zip` — код, шаблоны, внутренние руководства и
  тестовые исходники;
- `AI_FOUNDRY_BUILDER_GUIDE.md` — компактная точка входа, идентичная файлу в
  корне ZIP.

## Обязательный закрытый процесс

1. Распакуй текущий ZIP в новую пустую временную папку.
2. Убедись, что корень содержит одну папку
   `Генератор JSON для импорта в FoundryVTT`.
3. Запусти `python project_audit.py` до изменений.
4. Внеси изменения только в распакованный проект.
5. Обнови профильные руководства и регрессионные проверки, если изменился
   контракт JSON или фактическое поведение.
6. Запусти профильные тесты, `python builder_app.py --self-test` и
   `python project_audit.py`.
7. Собери новый архив командой `python package_project.py`.
8. Упаковщик обязан повторно распаковать архив, сравнить точный состав и байты,
   затем запустить аудит из распакованной копии.
9. Заменяй прежний ZIP только если весь процесс завершён успешно.

Запрещено редактировать содержимое ZIP на месте, добавлять в него отдельный
«исправленный» файл или собирать архив из всей рабочей папки.

## PROJECT_MANIFEST.json

`canonical_files` — единственный разрешённый список файлов исходного проекта.
Упаковщик включает только его и сам `PROJECT_MANIFEST.json`.

При изменении манифеста:

- пути должны быть относительными, безопасными и уникальными;
- каждый путь должен указывать на обычный файл внутри корня проекта;
- новый файл добавляется только если он является постоянной частью проекта;
- удалённый или переименованный файл удаляется и из манифеста;
- пользовательские JSON, настройки Foundry/Midi-QOL и временные результаты не
  становятся каноническими примерами без отдельного решения;
- `node_modules`, `__pycache__`, логи, кэши, отчёты и содержимое `output` не
  входят в исходный ZIP.

## Версии Foundry в импортах

`targets.foundry` — версия, на которой проект разрабатывается и проверяется.
`targets.export_core` — самая ранняя поддерживаемая сборка той же мажорной схемы.
Исходящие `_stats.coreVersion` всегда получают `export_core`, включая актёра и все
вложенные документы. Это не меняет `_stats.systemVersion`, которая нужна для
корректных миграций D&D5e.

## Генерируемые результаты

Устанавливаемые модули и отчёты сборки создаются по запросу и не хранятся как
исходники. Для усилений используется:

```bash
python build_enhancement_module.py enhancement_test_set.json
```

После сборки проверяются целостность ZIP, `module.json`, три LevelDB-пака,
`packFolders`, контроллер, точный набор документов и обратное соответствие
распакованных документов исходным.

## Замена без копий

Канонические имена неизменны. Не создавай `v2`, `final`, `fixed`, `(1)` и
подобные параллельные варианты. Если проверка не прошла, прежняя версия
остаётся актуальной.

Внешний `AI_FOUNDRY_BUILDER_GUIDE.md` и его копия в ZIP должны быть побайтово
идентичны. Любое изменение маршрута требует одновременной замены обоих
пользовательских файлов.
