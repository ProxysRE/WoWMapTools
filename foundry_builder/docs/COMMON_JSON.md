# Общий AI-контракт JSON

Версия формата: 4.0

Применяй эти правила ко всем первичным JSON для `builder_app.py`, затем открывай
профиль сущности.

## 1. Источник структуры

- Всегда начинай с нужной секции `templates.json`.
- Не удаляй обязательные поля шаблона и не создавай сырые `_id`, UUID, `flags`
  или готовые Foundry activities.
- До сборки `system.activities` остаётся пустым объектом `{}`.
- Декларативная механика находится в корневом `mechanics`; билдер компилирует
  её и удаляет это служебное поле.
- `system.description.value` содержит полное игровое правило. Технические поля
  и `chatFlavor` его не заменяют.
- Пассив без автоматизации может не иметь `mechanics`. Любая поддерживаемая
  активная часть должна быть размечена, а не оставлена только в описании.

## 2. Activities

Допустимые общие типы: `attack`, `save`, `damage`, `heal`, `utility`; отдельные
профили могут разрешать `cast`.

Одна нажимаемая часть — одна activity. Разделяй механику, если у частей разные
моменты броска, цели или условия: например, атака сейчас и урон в начале
следующего хода.

Активация:

| Момент | `activation.type` | `value` |
|---|---|---:|
| Действие | `action` | `1` |
| Бонусное действие | `bonus` | `1` |
| Реакция | `reaction` | `1` |
| Легендарное действие | `legendary` | стоимость |
| Действие логова | `lair` | `1` |
| Условная/вспомогательная кнопка | `special` | `null` |
| Без активации | `none` | `null` |

Для `reaction` и `special` записывай точный триггер в
`activation.condition`.

Составные `feat`, `spell` и `equipment` используют `targeting`; оружие
использует профильное поле `range`. Точную форму смотри в соответствующем
руководстве.

## 3. Урон, спасброски и лечение

- Формула содержит все выпадающие кости и фиксированные модификаторы:
  `"1d8+7"`, а не среднее значение и не `"1d8"` при текстовом `+7`.
- Каждый компонент урона имеет английский системный тип.
- Спасбросок содержит характеристику и числовую Сл; только заклинание может
  использовать `"dc": "spellcasting"`.
- `on_save` задаёт результат успеха: `none`, `half` или поддерживаемый
  профильным билдером вариант.
- Урон без атаки и спасброска — `damage`, лечение — `heal`, временные хиты —
  лечение типа `temphp`.
- `utility.roll` применяется только к броску, который не является атакой,
  уроном, лечением или спасброском.

## 4. Ресурсы и длительность

Общие использования задаются в `system.uses` или `mechanics.uses`. При
нескольких activities ресурс расходует только фактическая кнопка активации;
вспомогательные броски не списывают его повторно. Для иной схемы явно используй
`consume_uses`, `consumption`, `spell_slot` или собственные `uses` activity
согласно профильному руководству.

Периоды восстановления: `recharge`, `sr`, `lr`, `day`, `dawn`, `dusk`.
Для перезарядки 5–6 используй период `recharge` и формулу `"5"`.

Единицы длительности: `turn`, `round`, `minute`, `hour`, `day`. Мгновенную
длительность можно не задавать.

## 5. Active Effects

- Эффект владельца предмета: `transfer: true`, без привязки к activity.
- Эффект выбранной цели: `transfer: false` и явная привязка к activity.
- Стандартное состояние указывается английским ID; изменение параметра —
  точным системным путём в `changes`.
- Эффект при провале спасброска использует `on_save: false`.
- Если у сущности несколько activities, укажи правильный селектор `activity`.
- При `system.attributes.ac.calc: "flat"` меняй
  `system.attributes.ac.flat`, а не `system.attributes.ac.bonus`.

## 6. Ручная механика

Не обещай автоматизацию без поддерживаемого контракта. Сохраняй полным текстом
и отмечай как ручные сложные триггеры, ауры, принудительное перемещение,
телепортацию, призыв, превращение, изменение максимума хитов, запрет лечения,
условное падение до 0 хитов и автоматический запуск одной activity другой.

Мультиатака остаётся `feat` с `utility`: она не запускает дочерние атаки
автоматически. Каждый вариант легендарного действия — отдельный `feat`; запас
хранится в ресурсе актёра `legact`.
